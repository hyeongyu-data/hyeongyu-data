# 01. Auto Research
## ML 실험을 실행할 인프라 만들기

**2026.06–08 · 8주 · 5인 팀 · 인프라 전담**

[인프라](https://github.com/SKYAHO/Autoresearch-infra) · [애플리케이션](https://github.com/SKYAHO/Autoresearch) · [Airflow](https://github.com/SKYAHO/Autoresearch-airflow)

### 프로젝트와 담당 범위

가설을 입력하면 AI 에이전트가 Kubernetes에서 ML 실험을 실행하고 리포트를 생성하는 팀 프로젝트입니다. 저는 GCP 리소스, CI 인증, 배포, 관측 환경을 담당했습니다. 모델·애플리케이션과 Airflow 업무 로직은 팀의 다른 담당 영역입니다.

<div class="flow"><b>Terraform · GitHub Actions · WIF</b><span>↓ 인프라 구성 및 배포 권한</span><b>GCP · GKE · Cloud SQL · Artifact Registry</b><span>↓ 실행 상태 관측</span><b>Prometheus / Grafana · ELK</b></div>

### 초기 환경 구축

실험 코드가 실행될 개발 환경부터 구성해야 했습니다. VPC·GKE·Cloud SQL·Artifact Registry와 CI 인증·저장소 기반을 Terraform으로 관리했습니다. 초기 리소스 25개를 1주일 내 적용했고, 당시 `terraform plan`의 `No changes`로 코드와 배포 상태가 일치함을 확인했습니다.

### 관측 공백 해소

GKE·Airflow·MLflow·서빙의 상태를 함께 확인할 수 있도록 관측 작업을 8개 이슈로 나눴습니다. Prometheus/Grafana와 ELK를 1.5일 내 배포·검증하고, 실제 런타임 메트릭과 로그에 맞춰 수집 설정과 대시보드를 조정했습니다.

### 배포 절차와 보안

- Terraform apply 진입점을 2개에서 1개로 통합하고 8개 root를 한 번의 승인으로 적용하도록 정리했습니다.
- 서비스 계정과 WIF 권한은 분리하고 OAuth allowlist를 Kubernetes Secret으로 이관했습니다.
- Claude Code PR 리뷰에 IAM·시크릿·배포·롤백·비용 항목을 포함했습니다. 리뷰 의견에는 실행 결과와 코드 근거로 답변하도록 했습니다.

**확인 범위** — 교육과정의 개발 환경에서 구축·운영한 경험입니다. 초기 배포 시점의 상태 확인을 지속적인 무장애 운영 성과로 표현하지 않았습니다.

# 01. Auto Research
## 장애에서 확인한 코드와 실행 상태의 차이

### 사례 A · Airflow crash-loop

**증상** — Airflow가 45시간 동안 정상 실행되지 못하고 재시작을 반복했습니다.

**원인** — 오래된 로컬 `tfvars`가 잘못된 Cloud SQL 대역을 NetworkPolicy에 적용했습니다. 저장소의 설정과 실제 적용에 사용된 값이 달랐습니다.

**대응** — 연결 대상과 적용된 네트워크 정책을 대조해 원인을 좁혔습니다. 권한 변수 누락 등 유사한 설정 사고 3건도 분석해, 설정과 적용 상태의 불일치를 재발 방지 과제로 정리했습니다.

**배운 점** — 장애 시 애플리케이션 로그만 보는 것으로 충분하지 않았습니다. 어떤 입력값이 어떤 리소스에 적용됐는지까지 확인해야 했습니다. 45시간은 장애 지속 시간이며, 복구에 걸린 시간이나 단축 성과를 뜻하지 않습니다.

### 사례 B · 환경 재구축 후 admission 403

**증상** — 환경을 다시 만든 뒤 배치 실행이 admission 403으로 실패했습니다.

**원인** — 이전 환경에서 수동으로 생성한 Kubernetes Service Account가 재구축 과정에 포함되지 않았습니다.

**대응** — 해당 계정을 Terraform 관리에 편입했습니다. 복구 과정에서 먼저 만든 리소스는 state로 가져와 실제 환경과 관리 코드가 중복되지 않도록 정리했습니다.

**개선** — 다음 환경 구성 시 필요한 계정을 코드로 함께 생성할 수 있게 했습니다. 임시 복구에서 끝내지 않고 재구축 절차에 반영한 사례입니다.

### 이후 작업에서 적용하는 점검 순서

<div class="flow"><b>증상 · 로그 확인</b><span>↓</span><b>설정 입력값 ↔ 실제 리소스 비교</b><span>↓</span><b>복구 후 관리 코드 · 운영 문서 반영</b></div>

문제가 발생한 지점과 변경 이력을 먼저 확인하고, 코드·권한·네트워크·실행 상태를 연결해 원인을 설명하려고 합니다. 복구가 끝나면 같은 조건에서 다시 배포할 때도 필요한 설정이 유지되는지 점검합니다.

# 02. Air Quality Project
## 데이터가 없거나 처리가 실패해도 구분할 수 있게

**2026.04–09 · 개인 프로젝트 · 로컬 Docker 환경**

[저장소 및 실행 문서](https://github.com/hyeongyu-data/air-quality-project)

기상청·에어코리아 데이터를 하루 4회 수집해 상태를 분류하고 알림을 보내는 파이프라인입니다. 데이터 수집부터 저장·알림까지의 실패 상황을 직접 다뤄보기 위해 구성했습니다.

<div class="flow"><b>Airflow → 기상청 · 에어코리아 API</b><span>↓ 수집 이벤트</span><b>Kafka → 소비자 · 상태 분류</b><span>↓ 처리 결과</span><b>OpenSearch · 카카오 / 이메일 / Slack</b></div>

### 결측값을 정상 수치로 만들지 않기

결측값을 0으로 바꾸면 대기질이 좋은 것으로 오해할 수 있습니다. 값이 없으면 `UNKNOWN`으로 분류하고 화면과 알림에서는 정보가 없음을 표시합니다. 미세먼지 두 지표가 모두 없을 때는 외부 알림을 억제하되 처리 이력을 남깁니다.

### 실패 후 다시 처리할 수 있게 만들기

- 결정적인 event ID를 문서 키로 사용해 OpenSearch에 upsert합니다.
- Kafka는 처리 완료 후 수동 커밋하고, 잘못된 메시지는 DLQ와 스키마 계약으로 다룹니다.
- 상태 변화에 따라 알림을 보내며, 전송 성공 시에만 중복 억제 상태를 기록합니다. 모든 채널이 실패하면 다음 처리에서 재시도할 수 있게 했습니다.
- 재연결 대기와 소비자 종료 처리를 구현하고, 시크릿이 로그에 노출되지 않도록 마스킹했습니다.

### 검증과 기술 선택

로컬에서 실제 데이터 수집·알림 수신을 확인했습니다. 2026년 9월 15일 회귀 테스트 248개 통과를 확인했으며, CI에서 ruff·pip-audit·gitleaks·hadolint 등을 실행하도록 했습니다.

하루 4회 수집에는 Kafka·OpenSearch가 필수적이지 않습니다. 이 프로젝트에서는 이벤트 처리와 검색·관측 구조를 학습하기 위해 사용했고, 더 단순한 대안과의 차이를 ADR에 기록했습니다. 로컬 검증 결과를 대규모 트래픽 처리 성과로 해석하지 않습니다.

# 03. Ecommerce ETL
## 서로 다른 주문 데이터를 같은 계약으로 다루기

**2026.09–진행 중 · 개인 프로젝트 · 2026.09.15 기준**

[저장소 및 스키마 문서](https://github.com/hyeongyu-data/ecommerce-etl-pipeline)

이커머스에서 결제·오픈마켓 데이터를 통합 조회한 경험을 바탕으로, 수집·정제·적재 과정을 재현 가능한 개인 프로젝트로 구현하고 있습니다. 원천 데이터는 합성 데이터와 로컬 목업을 사용합니다.

<div class="flow"><b>합성 PG CSV · 목업 오픈마켓 HTTP · GA4 목업 보고서</b><span>↓ 원천별 Airflow DAG 3개</span><b>18개 컬럼 통합 스키마 · 품질 검사 · Parquet</b><span>↓ 별도 수동 실행 DAG</span><b>DuckDB 날짜별 적재 모듈</b></div>

### 수집·정제 구현

- PG·오픈마켓·GA4 입력을 원천별 DAG로 분리했습니다. 오픈마켓은 로컬 HTTP API를 호출하며 타임아웃과 재시도를 처리합니다.
- 원천별 필드를 통합 주문 스키마로 매핑하고 날짜별 Parquet staging과 품질검사를 구성했습니다. PG·오픈마켓은 저장 후 검사하고 GA4는 검사 통과 후 저장합니다.
- GA4 목업 보고서는 헤더·스키마·날짜·금액·중복 항목을 확인합니다. 정상적인 0행 결과와 손상된 보고서·수집 실패를 구분합니다.

### DuckDB 적재 구현

세 원천의 staging을 읽고 공통 품질검사 후 DuckDB에 적재하는 수동 실행 DAG를 구현했습니다. 트랜잭션으로 대상 날짜를 삭제·삽입하며, 정상 입력을 같은 날짜에 재실행했을 때 중복 없이 유지되는지 확인했습니다. BigQuery는 설계 목표로 남겨두었습니다.

### 검증 범위와 후속 작업

| 구분 | 현재 범위 |
|---|---|
| 수집 입력 | 합성 PG · 로컬 오픈마켓 API · GA4 목업 보고서 |
| 기존 Docker E2E | PG 46·오픈마켓 45·GA4 61 = 152행, 재실행 중복 0 |
| 현재 적재 | DuckDB · 수동 통합 DAG · 공통 품질검사 |
| 후속 작업 | BigQuery·실제 GA4 API 연결, 분석 대시보드 |

09.15 pytest는 91개 통과·1개 스킵입니다(Airflow 미설치). E2E는 기존 Docker 검증 기록입니다. 적재 함수 직접 호출의 대상일 혼입·부분 입력과 동시 실행은 추가 검증이 필요합니다.

# 04. Construction Risk Agent
## 질문에 필요한 계산을 선택하고 결과를 합성하기

**2026.06 · 5인 팀 · 라우터·결과 합성·장비비 에이전트 담당**

[포트폴리오 저장소](https://github.com/hyeongyu-data/construction-risk-agent)

기상·공정 지연·자재 리스크에 따른 추가공사비를 산정하는 LangGraph 기반 팀 프로젝트입니다. 저는 질문을 어떤 노드에 전달할지 결정하는 실행 흐름, 결과 합성, 장비 대기비 계산을 맡았습니다.

<div class="flow"><b>질문 · 직전 대화 맥락</b><span>↓</span><b>플래너 기반 라우터 → 필요한 비용 노드</b><span>↓</span><b>synthesize → 비용 리포트 · 구조화된 응답</b></div>

### 고정 분기에서 동적 라우팅으로

초기 고정 A/B 분기를 플래너 기반으로 바꾸고, 질문과 이전 대화 맥락에 따라 필요한 비용 노드만 호출하도록 라우터·그래프·상태 흐름을 설계하고 구현했습니다.

### 여러 결과를 하나의 응답으로

`synthesize` 노드와 답변 유형별 few-shot 예시를 작성했습니다. 각 노드의 결과를 비용 리포트와 구조화된 응답으로 합성할 수 있도록 구성했습니다.

### 장비 대기비 계산

장비명 정규화 → 규격 매칭 → 일대여료 조회 → 대기율·일수 반영 순서로 로직을 구현했습니다. 계산에 필요한 PostgreSQL 스키마·초기 적재 데이터와 테스트를 함께 작성했습니다.

**담당 기술** — Python, LangGraph, AWS Bedrock, PostgreSQL

### 협업 범위

백엔드 인증, 프런트엔드, 날씨·자재·인건비 노드는 다른 팀원의 담당 영역입니다. 제 기여는 공통 실행 흐름과 결과 합성, 장비비 계산에 집중했습니다.

### 함께 일할 때
